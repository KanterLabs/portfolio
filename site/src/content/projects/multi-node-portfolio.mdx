## Overview

The portfolio is intentionally static. The operational work is in making one
small artifact deploy safely to two independent origins, keeping the beta lane
private, and recovering without rebuilding a server by hand.

Production is **Cloudflare → load-balanced OVH and homelab origins**. Each
origin serves the same commit-addressed Astro release through Nginx. The OVH
path includes the shared Caddy edge; the homelab origin has its own reviewed
ingress path. Neither public route is used for deployment.

## Current Architecture

```text
Internet
   |
Cloudflare DNS, CDN, Full (strict) TLS, and health checks
   |
Cloudflare Load Balancer
   |                         |
OVH edge → Nginx          Homelab ingress → Nginx
   \_________________________/
        identical immutable release
```

## Why This Shape

The public edge and the workload should not share an operational boundary. A
single origin was simple, but it made a maintenance event or failed host a
single point of failure. The current design adds a homelab origin without
making either origin responsible for public DNS, load-balancer policy, or the
other origin's state.

The resulting boundary is small and explicit:

- Cloudflare health checks and load balancing decide which production origin
  receives public traffic
- each origin accepts only its reviewed ingress and management peers
- OVH is reached over private management SSH; homelab is reached through the
  reviewed jump host
- neither workload runs Docker, Tailscale, or a public deployment listener

## Atomic Delivery

GitHub Actions builds and tests the Astro site on an ephemeral homelab runner.
A beta push produces one compressed artifact and sends it directly over private
management paths to the beta account on each origin. Beta is deliberately not a
load-balancer backend: it has no public DNS record, Tunnel, Funnel, or public
worker route.

The remote account cannot open a shell. It can only request the fixed deploy,
verify, promote, activation, and rollback commands. Each helper validates the
archive, extracts it into a commit-addressed release, validates its local
private HTTPS health endpoint, and atomically swaps the relevant `current`
symlink. A failed local check restores the prior symlink.

When `beta` merges to `main`, the workflow stages the tested main artifact in
both private candidate lanes and verifies its SHA and content there. Both
production origins then prepare that exact digest before either activates it.
If activation on one origin fails, the workflow rolls both origins back to
their recorded prior release. Retained releases make rollback independent of
GitHub, npm, or a rebuild.

## TLS and Health

Cloudflare uses **Full (strict)** origin mode and health-checks the two public
origins. The apex and `www` hostnames are served through the production pool,
with `www` redirecting to the canonical apex. Both origins use their own
private origin identity and trust chain.

Nginx exposes `/healthz` with an exact `ok` response. The deployment helper
checks the private vhost after activation, while Cloudflare monitors the public
origins. That separates release, origin, and edge failures instead of treating
the site as one opaque endpoint.

## Recovery

The deployment has three recovery layers:

| Failure                      | Recovery                                                                    |
| ---------------------------- | --------------------------------------------------------------------------- |
| Bad release on either origin | Roll both origins back to retained commit-addressed releases                |
| Failed origin                | Cloudflare health checks remove it while the other origin continues serving |
| Broken workload              | Restore that origin's verified backup without changing the other origin     |

## Architecture Evolution

The first version used two GCP `e2-micro` origins behind a paid Cloudflare Load
Balancer. That design was useful for learning Terraform, multi-zone origins,
and health checks. Over time the second origin became disabled, leaving the
published redundancy claim out of step with reality.

The initial homelab migration simplified that to one private origin while the
delivery controls matured. The current iteration restores real redundancy with
two active origins and makes it part of the normal beta and promotion workflow,
rather than a standby path that is never exercised.

## What It Shows

- **Linux operations:** two hardened services with narrow firewall rules
- **Network design:** public load balancing, ingress, and private workloads have separate roles
- **Delivery engineering:** build once, validate twice, and promote the exact artifact
- **Recovery design:** coordinated release rollback plus origin-level failover
- **Operational honesty:** the public writeup describes the deployment that actually runs
