## Overview

This portfolio runs as a static Astro build served by Nginx in a container.
Coolify operates separate beta and production applications on an OVH app host.
GitHub Actions builds the image, publishes it to GHCR, and tells Coolify exactly
which immutable digest to deploy.

The important distinction is between building a release and running it:
Coolify does not rebuild the source or deploy a mutable branch tag. Every
running image can be traced to a tested Git commit.

## Current Architecture

Production requests follow **Cloudflare → Cloudflare Tunnel → the Coolify
application's Nginx container**. The tunnel connector forwards traffic to the
application's loopback port, so the app host keeps inbound web ports closed.

The chatbot is a separate production-only Cloudflare Worker on `/api/chat*`,
with retained D1 conversation history. Its code and reviewed knowledge require
a separate Worker deployment; publishing the static site alone does not update
chatbot answers.

## Beta Before Production

A push to `beta` runs dependency audits, Worker validation, browser tests, and
container smoke tests. CI publishes an immutable image, then deploys that
exact digest to the beta application. Beta uses a private hostname reached
over the tailnet and has no public DNS record.

Production promotion comes from a pull request from `beta` to `main`. After
merge, the main workflow repeats validation, builds and smoke-tests its own
commit-tagged image, and deploys the resulting digest to production. The two
lanes use separate Coolify application identities, credentials, and protected
GitHub environments. A stale workflow cannot replace a newer release: the
job checks that its commit is still the branch tip before deployment.

## Exact-Digest Deployment

The deployment helper first checks the target application's identity,
environment, server, destination, port, and existing image digest. It records
the previous digest before changing anything.

It then sets the requested digest, starts a Coolify deployment, and waits for
completion. Success requires all three checks:

- Coolify reports the application healthy.
- `/healthz` returns `ok`.
- `/_meta/revision` matches the requested Git commit.

Production checks go through the public hostname, exercising Cloudflare, the
tunnel, and the application together. If verification fails after the image
changes, the helper restores and redeploys the recorded previous digest.

## Public Ingress, Private Deployment

The public tunnel carries site traffic. Protected deploy jobs reach the
Coolify API and private beta verification URL through the tailnet. Deployment
credentials are supplied at runtime and are not part of the static site or
container image.

This keeps the release path separate from the public request path while
letting production verification prove that visitors receive the right build.

## Architecture Evolution

Earlier versions used static Nginx origins on GCP, then OVH and the homelab,
with Cloudflare load balancing and coordinated artifact promotion. Those
were earlier deployments, not the current production topology.

The current Coolify workflow replaces direct artifact uploads and symlink
activation with immutable container releases. The retired static-origin load
balancer remains disabled as an emergency recovery option; it is not active
production failover.

## What It Shows

- **Delivery engineering:** tested, commit-tagged images deployed by exact digest.
- **Environment isolation:** separate beta and production applications and credentials.
- **Network boundaries:** public tunnel ingress and private deployment access.
- **Recovery:** live verification and automatic return to the previous image.
- **Operational accuracy:** the case study and chatbot describe the deployment that runs.
