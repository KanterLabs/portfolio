## Overview

My homelab grew from a development server into a small platform spread across two Proxmox environments. Each site now has a purpose-built edge boundary: the home environment supports development, CI, secrets, and selected origins, while the remote environment carries production application workloads and Internet-facing routing.

The interesting part is not the machine count. It is the set of boundaries around them:

- public traffic enters through dedicated Cloudflare paths instead of reaching workloads directly
- private applications have separate Tailnet-only names and listeners
- management, ingress, and origin networks are distinct planes with default-deny forwarding
- edge services bind to exact interfaces, and private DNS answers only on the intended views
- ActionRunners gives each enrolled Gitea Actions job a disposable Proxmox VM
- credentials live outside Git and are injected only where they are needed

## Problem

As the homelab expanded across two Proxmox environments, loosely coupled ingress rules and persistent repository runners made the platform harder to reason about. I needed explicit public and private entrances, isolated management and workload networks, and changes I could recover from if a firewall or route was wrong.

## My Contribution

I designed and built the edge boundaries, network policy, private DNS and TLS, and the ephemeral CI platform described here. I put selected infrastructure configuration into a reviewed repository and kept host changes behind guarded apply steps, with management-path checks and timed rollback. Secrets remain outside Git.

## Result and Evidence

The platform has named traffic paths with positive canaries for allowed access and negative tests for unwanted exposure. The architecture diagrams below show the two-site layout, trust boundaries, and repository responsibilities.

The infrastructure repository is private, so this article exposes the design and its verification approach without offering private configuration or live operational data. The [public portfolio source](https://github.com/KanterLabs/portfolio) contains the diagrams used here.

## How the Infrastructure Repository Fits

The private `KanterLabs/infrastructure` repository is the **reviewed source of truth for selected infrastructure**, not a complete inventory and not a continuously reconciling GitOps controller.

That distinction matters. A merged change records the intended configuration and gives me something reviewable, testable, and recoverable. It does not automatically rewrite every target host.

| Repository area | What it describes | How it reaches runtime |
|---|---|---|
| Edge configuration | Exact Caddy listeners, split-horizon DNS, Tailnet policy, and workload interfaces | Rendered from reviewed plans, validated, and deliberately installed on each edge VM |
| Workload policy | Host firewall rules and private/public service bindings | Applied on the relevant workload |
| Hypervisor networking | VLAN-aware bridges, NAT, forwarding allowlists, and isolation between planes | Installed through guarded host-managed transactions |
| CI platform | ActionRunners controller, VM templates, fleet policy, and isolation checks | Applied with versioned scripts and qualified with Gitea Actions canaries |

Deployment keys and service tokens are provisioned outside Git through scoped service credentials, Infisical, or restricted files.

<Callout type="note" title="Reviewed does not mean automatic">
  The repository makes changes inspectable and repeatable, while the install scripts preserve an explicit operator checkpoint. That is a deliberate tradeoff for a small environment where an incorrect firewall or ingress change can disconnect the very host needed to repair it.
</Callout>

## Four Ingress Planes, Two Edge Boundaries

The edge VMs own application ingress. Workloads do not receive arbitrary inbound traffic from the Internet, the Tailnet, management networks, or neighboring workload zones. The platform verifies four independent HTTPS planes: remote public, remote private, home public, and home private.

### Public path

At the remote site, public requests pass through Cloudflare, reach the hypervisor's narrow forwarding boundary, and are sent only to the edge VM's public interface. At home, a connector creates outbound transport to Cloudflare without opening unsolicited inbound access. In both cases, Caddy accepts only intended hostnames and proxies to the matching origin.

Origins live behind those boundaries. Their host firewalls permit application traffic from the relevant edge source, not from an entire LAN or VLAN. TLS is re-established and verified on sensitive edge-to-origin paths rather than assuming that internal transport is trusted.

### Private path

Private applications use named Tailscale services or deliberately retained Serve routes as their only entrance. Tailscale hands traffic to loopback-only or explicitly bound Caddy listeners, while split-horizon DNS prevents private names from becoming public discovery paths. Direct Tailnet routing into workload networks is not a substitute for the named service entrance.

### Zone policy

The design separates four concerns:

1. **management** for administration during the migration period
2. **ingress** for edge-facing listeners and transport connectors
3. **public origins** for services intentionally reachable through a public edge path
4. **private origins** for Tailnet-only applications

Forwarding between those planes is denied by default and opened only for named flows. Edge input, forwarding, and output policy fail closed; interfaces and source addresses are matched explicitly. Public and private origins can receive the traffic they need, but they cannot route laterally or use management as an alternate application entrance.

The same policy is exercised negatively: unknown hostnames, incorrect TLS names, cross-plane requests, plaintext origin access, spoofed proxy identity, and direct workload access must fail. Synthetic canaries prove each approved plane without depending on an application migration.

## Disposable CI Runners

ActionRunners polls Gitea and provisions a Proxmox VM from a reviewed template when there is room for the job. The guest receives one single-use runner registration. After the job ends, the guest shuts down and the controller reclaims it. The [ActionRunners case study](/projects/actionrunners) walks through provisioning, isolation, cleanup, and the live dashboard.

## Security Decisions

The host firewall isolates runner guests from the LAN and management network. Reusable runner registration credentials stay on the controller even when a job builds and runs containers inside its VM.

Network configuration is rendered deterministically, rejected if it contains wildcard binds or unapproved routes, and applied through a guarded transaction. A timed rollback protects the change until management-path checks, configuration hashes, service health, positive canaries, and negative exposure tests pass.

## What I Learned

The largest improvement came from treating infrastructure as a set of contracts instead of a collection of machines.

- **Ingress contract:** every application has one intended entrance.
- **Network contract:** every allowed flow names its source, destination, interface, and purpose; everything else fails closed.
- **Name and TLS contract:** public and private DNS views, hostnames, and certificates agree with the traffic plane.
- **CI contract:** Each admitted job gets a single-use runner and a VM sized for its workload.
- **Repository contract:** reviewed files describe intended state, while secrets and host-local state remain outside Git.
- **Recovery contract:** network changes keep an automatic rollback and an independently tested management path until the replacement has been exercised.

The result is still a homelab—small, resource-conscious, and operated by one person—but it now behaves like a platform I can reason about, review, and extend.
