## Overview

ActionRunners gives each enrolled Gitea Actions job its own Proxmox VM. The controller clones a reviewed template, delivers a single-use runner registration, and reclaims the VM after the job. Each clone starts with a fresh workspace and Docker state. Selected projects can reuse explicitly shared build caches.

A small controller makes that happen. It polls Gitea, admits jobs against one capacity ledger, and reports to a live dashboard that shows each job moving through its lifecycle.

## Problem

Long-lived CI workers retain their runner registration and can accumulate toolchain and workspace state between jobs. I wanted each job to start in a fresh environment, with a smaller VM for quick checks and more resources for browser tests and container builds.

## My Contribution

I designed and built the controller, the VM templates, the host firewall for runner VMs, and the dashboard. The controller records each reservation in a durable ledger. A separate cleanup pass uses that record to recover after interrupted provisioning or a crash.

Two properties make the lifecycle safe to automate.

- **Admission happens before cloning.** A job that would push the fleet past its VM, vCPU, or memory ceilings, or eat into the host's memory reserve, simply stays queued. The controller logs the reason, and the dashboard shows it on the waiting job's card.
- **Cleanup can recover after a crash.** The controller reclaims a VM after its runner exits and the guest shuts down. A separate janitor pass reclaims owned guests that are stopped, past their lease deadline, or missing from the ledger.

## Runner Isolation

The controller uses scoped Proxmox permissions and touches only designated runner resources. It delivers the single-use runner file through the QEMU guest agent and keeps the reusable registration credential on the controller. Host-level firewall rules keep job guests away from management services and other private workloads.

Portfolio uses separate runner profiles for validation and protected releases. Release jobs run in a trusted repository, with their deployment credentials kept out of ordinary pull-request jobs.

<Callout type="note" title="Fail fast on pull requests">
  Repositories can opt in to fail-fast cancellation. When a job in an opted-in pull request run fails, the controller cancels the rest of that run, so its VMs are released early and the pull request turns red without waiting for the slowest job. Push and scheduled runs always run to completion so they report every failure.
</Callout>

## Watching the Fleet

The dashboard shows each job's current stage, why queued jobs are waiting, how long VMs take to become ready, and how runs compare with the old dedicated runner.

The controller pushes snapshots and lifecycle events to the dashboard. The dashboard stores them in SQLite and sends refresh notices to open browsers through server-sent events. It holds no Proxmox or Gitea credentials.

The dashboard is plain HTML, CSS, and JavaScript with hand-drawn SVG charts and no third-party packages. Its content security policy allows only same-origin scripts and styles, so every chart sets its geometry through the CSSOM rather than inline styles. It follows the system's light or dark theme and stacks the board into a single column on a phone.

## Result and Evidence

In a 24-hour production sample recorded on November 16, 2026, the controller completed **105 VM provisions**. From admission to readiness, the median was **18.6 seconds** and the 95th percentile was **23.0 seconds**. This interval covers provisioning and runner registration up to readiness. Queue time and job execution are measured separately.

For the Portfolio cutover, canary jobs verified checkout, artifact upload and download, container builds, and denied private routes. The controller's lifecycle records showed that VMs from both the validation and release templates were reclaimed.

## What I Learned

- Polling keeps the forge from needing an inbound path to the controller.
- Reserving resources before cloning protects host capacity when several workflows arrive together.
- Showing why a job is queued makes it easier to tell when the fleet is at capacity or provisioning has stalled.
